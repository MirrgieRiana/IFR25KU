# リリース

## リリースの引き金

リリースは、`v` で始まるタグが push されたときにのみ、`release` ワークフローによって開始されます。
それ以外の操作では、一切開始されません。

## 人間が行う手順

以下の 3 段は、すべて人間が行います。
AI エージェントは、指示された場合を除き、これらを行ってはいけません。

### 1. 更新履歴の見出しの確定

更新履歴の「未リリース」の見出しを、これからリリースするバージョン番号へ書き換えて、コミットします。
これは、下のバージョン番号のコミットとは別のコミットであり、その前後のどちらに置いてもかまいません。
更新履歴の記述先と記述内容については、`changelog` スキルを参照してください。

### 2. バージョン番号の書き換えとコミット

`gradle.properties` の `mod_version` を、これからリリースするバージョン番号へ書き換えます。
この値には、`v` を付けません。

そして、その 1 行の変更だけを、`v` で始まるバージョン番号そのものをタイトルとするコミットとして、デフォルトブランチへ積みます。

### 3. タグの作成と push

そのコミットに対して、`v` で始まるバージョン番号のタグを作成し、push します。
タグの名前は、`gradle.properties` の `mod_version` の値の頭に `v` を付けたものでなければなりません。

この 2 個が食い違うと、ワークフローが探す jar のファイル名と、実際に生成される jar のファイル名が一致せず、リリースが失敗します。

## ワークフローが行う処理

タグが push されると、以下の処理が自動で行われます。

| 段 | 内容 |
| --- | --- |
| ビルド | `./gradlew :fabric:build :neoforge:build` を実行します。 |
| GitHub Release の作成 | タグ名と同じ名前のリリースを作成し、Fabric と NeoForge の 2 個の jar を添付します。 |
| 配布サイトへのアップロード | `./gradlew upload` によって、Modrinth と CurseForge へ送ります。 |

アップロードに用いるトークンは、リポジトリのシークレットから供給されます。

## 失敗したときの扱い

ワークフローは、同じタグに対して多重に走らないように構成されています。
そのため、失敗した場合は、そのワークフローの再実行によって復旧させます。
